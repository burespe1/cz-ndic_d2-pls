== Concepts

The format publishes sets of predefined locations – road network sections referenced by other NDIC
formats. A referencing message carries only the identifier and version of the location; the full
location description is in this publication.

[cols="2,3,3",options="header"]
|===
|Set (distribution) |Content |Referenced by
|`x-source:cz-ndic_d2-pls-fcd-pull-v2` |sections between ALERT-C locations, each direction separately |`cz-ndic_d2-fcd-status`
|`x-source:cz-ndic_d2-pls-weather-pull-v2` |road weather station sections, valid in both directions |`cz-ndic_d2-weather`
|===

A set is always downloaded as a whole (snapshot, pull). The format is based on the
`PredefinedLocationsPublication` publication <<EN16157-2>>.

[[obalka]]
=== Envelope and publication header

A message is a DATEX II 3 document with the root element `d2:payload` of type
`loc:PredefinedLocationsPublication`. The format is identified by the root attributes `profileName`
(`cz-ndic_d2-pls`) and `profileVersion` (`2.0`).

The header contains:

* `feedType` – the distribution according to the table above (reference to the register of the national
  access point <<nap>>),
* `publicationTime` – time the content was created; if the content has not changed, the original time is kept,
* `publicationCreator` – `cz` and `NDIC`,
* `headerInformation` – always `confidentiality` = `noRestriction` and `informationStatus` = `real`.

[[predef]]
=== Predefined locations

Each location is a `predefinedLocationReference` element of type `loc:PredefinedLocation` with a location
description (`location`, always linear – see <<polohy>>).

* The *identifier* (`@id`) is stable. FCD sections have it composed of ALERT-C locations:
  `TS25760T25761` is the section from location 25760 to location 25761, the opposite direction is
  `TS25761T25760`.
* The *name* (`predefinedLocationName`) is given only if the location has one in the source: road weather
  station sections carry the station name (`I/43 Černá Hora`, `D0 15.742`); FCD sections and groups have
  no name.
* The *version* (`@version`) corresponds to the Global Network release the set is derived from, in the form
  `YYMM01` (network 25.06 → `250601`). With each network release *all* locations of the set get a new
  version, including those where only the network version label (`linearElementReferenceModelVersion`)
  changed; the identifier stays. A new location gets a new identifier. Messages always reference the
  version of the current set.

The publication always contains all valid locations, including those published earlier. No time is given
inside the locations.

[[skupiny]]
==== Location groups

A group combines sections that are repeatedly referenced as a whole – also on different roads and
non-contiguous: an area of regular winter closures, a permanent diversion route, sections around a road
weather station.

.Group of three non-contiguous sections on two roads
image::skupina-poloh-en.svg[Location group – non-contiguous sections,width=640,align="center"]

A group is a `predefinedLocationReference` element of type `loc:PredefinedLocationGroup`. It is filled as
follows:

. The group gets its own identifier and version; no name is given.
. Each section of the group is a nested `predefinedLocation` element – a complete predefined location with
  its own identifier, version, location description and, where available, a name (the same as a
  stand-alone location).
. A group has at least two sections; their order has no meaning.
. Section identifiers are unique in the whole publication; the same section does not repeat within a
  group or the publication.
. If a section changes, both the section and the group get a new version; adding or removing a section
  changes the group version.

A message references the whole group with the type `loc:LocationGroupByReference` (`targetClass` =
`loc:PredefinedLocationGroup`). Predefined groups are created only for areas that recur; one-off area
events are described by the event formats with a group of sections directly in the message.

[[smer]]
=== Direction and bidirectional locations

A location is either one-directional or valid for both directions of travel:

* *FCD sections* are one-directional; each direction is a separate location (`TS25760T25761`,
  `TS25761T25760`).
* *Road weather station sections* and other bidirectional locations are described by *one* location for
  both directions. Each method expresses this in its own way:

[cols="1,4",options="header"]
|===
|Method |Bidirectional location
|ALERT-C |`alertCAffectedDirection` = `both` (one-directional `aligned`)
|OpenLR |`firstDirection` for the location direction and `oppositeDirection` for the opposite direction –
each with its own reference points and offsets (<<openlr>>)
|Global Network |sections shared by both directions once with `directionRelativeOnLinearSection` = `both`;
if the opposite direction runs elsewhere (separate carriageways, one-way sections), the whole route of the
opposite direction follows the route of the first direction (<<gn>>)
|===

Location groups are not used for bidirectionality. A pair of one-directional locations combined in a group
would require a different reference type (`LocationGroupByReference`), would lose the link between the
directions, and OpenLR and ALERT-C would express bidirectionality twice. Groups are reserved for areas.

[[polohy]]
== Location referencing

A location is linear (`loc:SingleRoadLinearLocation`) and is usually described by several methods depending
on their availability; all describe the same section and at least one must be given. FCD and road weather
station sections carry all three main methods.

A physically point-like place – a road weather station, a bridge, a tunnel entrance – is described as a
short road section on which it lies, in all methods alike: in ALERT-C as a section between two locations,
possibly with identical primary and secondary location; in OpenLR and the GN network as a section of
non-zero length around the place (OpenLR does not allow zero length). Point locations
(`loc:PointLocation`) are not used in the location sets.

[cols="2,3,3",options="header"]
|===
|Method |Element |For whom
|ALERT-C |`alertCLinear` |navigation with the RDS-TMC location table
|OpenLR |`openlrLinear` |matching to any map
|Global Network |`linearWithinLinearElement` (`LinearElementByCode`), `externalReferencing` |users of the GN network
|Road chainage |`linearWithinLinearElement` with `roadNumber` |not used yet
|===

=== ALERT-C location referencing

The location is given by two locations of the ALERT-C location table <<ISO14819-3>> in the `alertCLinear`
element of type `AlertCMethod2Linear`:

* table: `alertCLocationCountryCode` = `2` (Czech Republic according to IEC 62106),
  `alertCLocationTableNumber` = `25`, `alertCLocationTableVersion`,
* secondary location (`alertCMethod2SecondaryPointLocation`) – where the driver enters the section, primary
  (`alertCMethod2PrimaryPointLocation`) – where the driver leaves it,
* `alertCDirectionCoded` = `positive` if the direction of travel matches the coding direction of the
  location table,
* `alertCAffectedDirection` = `aligned` for a one-directional, `both` for a bidirectional location.

IMPORTANT: The meaning of `alertCDirectionCoded` is the opposite of the RDS-TMC `direction` bit.

[[openlr]]
=== OpenLR location referencing

OpenLR (`openlrLinear`) describes the location independently of any map: the consumer finds it in its own
map by searching a route between reference points. The reference points (`openlrLocationReferencePoint`,
the last one `openlrLastLocationReferencePoint`) carry WGS-84 coordinates, bearing, road class and distance
to the next point; the offsets `openlrPositiveOffset` and `openlrNegativeOffset` trim the found route to the
actual extent of the location.

A bidirectional location has both directions separately: `firstDirection` in the location direction and
`oppositeDirection` in the opposite direction, each with its own reference points and offsets. On a road
with separate carriageways each direction runs on a different carriageway:

[[gn]]
=== Global Network location referencing

The location is a list of sections of the Global Network (GN, ŘSD):

* Each section is a `linearWithinLinearElement` element with `linearElement` of type `LinearElementByCode`:
  `linearElementReferenceModel` = `CZ-RSD-GlobalNetwork`, `linearElementReferenceModelVersion` = network
  version, `linearElementIdentifier` = section identifier. Sections are in travel order.
* `directionRelativeOnLinearSection` – travel direction relative to the section coding, i.e. the direction
  in which the section was created in the GN database: `aligned` (along the coding), `opposite` (against the
  coding), for a bidirectional location `both` (the section serves both directions). The direction may
  alternate along a route so that the section ends connect – e.g. when the route passes a section created by
  coding another road that runs concurrently with it.
* One-way sections (e.g. separate carriageways, junction ramps) are always coded in the travel direction;
  they are therefore travelled only as `aligned` and a route never runs against them.
* `fromPoint` and `toPoint` are the points where the route enters and leaves the section. Within the route
  they are of type `PercentageDistanceAlongLinearElement` – percent of the section length (0–100) measured
  from the start of the section coding. For `aligned` the value increases (e.g. 20 → 100), for `opposite` it
  decreases (e.g. 100 → 20); a full section is 0 → 100 or 100 → 0.
* The start and end of the location (`fromPoint` of the first and `toPoint` of the last section) are of type
  `DistanceFromLinearElementReferent` and carry WGS-84 coordinates. The referent (`fromReferent`) is a known
  point lying on the section, given by coordinates (`pointCoordinates`); here it is the start or end of the
  location itself. `distanceAlong` is the distance of the described point from the referent along the
  section – since the referent is the point itself, it is always 0. It is not related to the start of the
  section: the position on the edge section is given by coordinates, not by percent. It replaces the
  `startPoint` and `endPoint` points of version 2 (there in S-JTSK).
* Full inner sections of the same direction are shortened to `externalReferencing` (`externalLocationCode`
  = section identifier, `externalReferencingSystem` = `CZ-RSD-GlobalNetwork:<network version>`). The complete
  route is then the first edge section, the inner sections in the order of `externalReferencing` and the
  last edge section.

==== Bidirectional location in GN

.Bidirectional location in GN – shared sections and separate carriageways
image::gn-obousmerne-en.svg[GN – bidirectional location,width=680,align="center"]

Sections shared by both directions (the opposite direction mirrors the first one) are given once with
direction `both`, in the order of the first direction and with its points: `fromPoint` → `toPoint`
describes travel in the first direction, so a decreasing value (e.g. 100 → 30) means that the first
direction runs against the section coding. The opposite direction is the same list read from the end, with
the points in reverse order. Only sections passable in both directions may have direction `both`.

The first section (3663224) runs from the start of the location (referent) to 0 %, the last section (901099)
from 100 % to the end of the location (referent); on both the first direction therefore runs against the
coding. Both full inner sections (1327329, 1326918) are shortened to `externalReferencing` at the beginning
of the location.

If the opposite direction runs elsewhere – on separate carriageways or on one-way sections (all `aligned`
in the example) –, the whole route of the first direction is given first, followed by the whole route of
the opposite direction, both as `linearWithinLinearElement` without shortening:

* Each route starts and ends with a referent with coordinates: the first direction runs from the start to
  the end of the location, the opposite direction from the end to the start. The last section of the first
  direction has a `toPoint` with a referent and the opposite direction starts after it.
* Each route is preceded by the XML comment `<!-- GN firstDirection -->` or `<!-- GN oppositeDirection -->`.
  The comment uses model element names (the same as in OpenLR), so it is language-neutral, and it is meant
  for human readers. A receiver should not rely on it; the boundary between the routes is given by the
  referent.

=== Road chainage location referencing

NOTE: Road chainage is in the profile for future use; the NDIC location sets do not contain it yet.

Road chainage is a `linearWithinLinearElement` element with the road number (`linearElement/roadNumber`),
the direction relative to the chainage (`directionRelativeOnLinearSection`) and the distance of the start
and end from the beginning of the road in metres (`fromPoint`, `toPoint` of type
`DistanceFromLinearElementStart`).
